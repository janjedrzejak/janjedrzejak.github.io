WebMCP on my site. From a counter to the AI Guide

2026-11-07JAN JĘDRZEJAK

I first heard about WebMCP at Google Cloud Summit Poland 2026, at PGE Narodowy in Warsaw. One fairly ordinary question stuck with me after the event. Could I type “Show AI projects” on a website and actually see the list update a moment later? Google Cloud Summit Poland 2026

I used my own portfolio to find out. It already had a project catalogue, filters, Polish and English versions, and a chat widget that could answer questions about the site. Everything I needed for a first test was already there. I just had to connect the conversation to the things the site could do. My portfolio

Letting the page say what it can do

An agent working through a regular website interface can look for a button much as a person would. It reads labels, looks through menus, and tries to work out what to click. On my site, it would have to find the projects page, locate the filters, and realise that “AI projects” means the one labelled “AI / ML”. That’s doable. On another site, the same filter might be tucked away in a dropdown.

WebMCP is a proposed web standard that lets a site expose specific functions in the open tab. Each tool has a name, a description, and a definition of the inputs it accepts. A site can offer a tool that applies a project filter and list the categories it accepts. A compatible agent can call it with the category ai. The page handles the details of applying the filter. Mine uses the same button a visitor can click by hand. Chrome’s WebMCP documentation · Portfolio tool code

What I like about this is that I can test the tool separately from the conversation. I can give it a specific value and see what the page does. Then I can ask whether the agent would pick the same function after reading an ordinary sentence.

The MCP in the name can be confusing

There is one distinction worth making here, because the name is slightly misleading. MCP and WebMCP are not the same thing, even though both let agents use tools. The original Model Context Protocol connects an agent to services, data and workflows, usually through an MCP server. An agent can query a database or start a backend process without visiting a website at all. MCP uses JSON-RPC messages and transports such as stdio and HTTP.

WebMCP, or Web Model Context Protocol, is a proposed browser API inspired by MCP, rather than “MCP running in JavaScript”. A tool runs in the context of an open page and its current user session. The browser makes that tool available to an agent that supports WebMCP. Close the tab and those page tools disappear. For now, WebMCP exposes tools, not the resources and prompts available in MCP. A page tool can still call a backend API, of course; that doesn't turn it into an MCP server.

For my experiment, the difference is fairly tangible. Asking to see AI projects doesn't contact a separate MCP server that manages my portfolio. It calls functionality already present on the website and I can see the result in the interface. The names sound related because the ideas are related, but the integration points are different. Chrome's MCP versus WebMCP comparison

I started with a counter

Before hooking up the chat, I built a separate WebMCP Playground. I could look through the tools, inspect the arguments they take, run a call, and see what came back. I added a simple counter, a way to change the accent colour, and a search tool for a small catalogue of sample projects. The counter was ideal. Send {"amount": 3} and watch zero turn into three. It’s hard to confuse that with a polite message saying everything went fine.

In Chrome with the experimental API available, the Playground shows Native mode. In a test, calling increment_counter through WebMCP moved the counter from zero to three. If the necessary API is unavailable, the Playground switches to Simulation and runs the functions locally. You can still play with the counter and inspect the inputs. The mode label tells you how the call ran. WebMCP Playground

To try it yourself, select increment_counter in the panel and run it with the default value of 3. The panel shows a history beside the result, and you can expand the input schema below the arguments field. For local testing, Chrome’s documentation points to the chrome://flags/#enable-webmcp-testing flag. Once you’ve enabled it and restarted Chrome, check that the panel says Native. Chrome’s testing instructions

A little JavaScript behind the scenes

I didn't need to build a second interface for the agent. With WebMCP's Imperative API, the page registers a tool using document.modelContext.registerTool(). Here's a shortened version based on my webmcp-site.js. The idea is the same as in the live portfolio: the agent supplies a category and the page clicks its existing filter button.

if ('modelContext' in document) {
  document.modelContext.registerTool({
    name: 'portfolio_filter_projects',
    description: 'Apply the project category filter.',
    inputSchema: {
      type: 'object',
      properties: {
        category: { type: 'string', enum: ['all', 'ai', 'automation', 'integration', 'product', 'commerce', 'data'] }
      },
      required: ['category'],
      additionalProperties: false
    },
    annotations: { readOnlyHint: false },
    execute: async ({ category }) => {
      const button = [...document.querySelectorAll('.filter-chip[data-filter]')]
        .find(el => el.dataset.filter === category);
      if (!button) throw new Error('Filter not found');
      button.click();
      return JSON.stringify({ success: true, category });
    }
  });
}

The important bit isn't click(). It's the contract: a name, description, inputSchema, and execute. The enum defines the categories the agent is expected to supply, and the code still checks that the filter exists. The full version also returns the number and names of visible projects. I only register this tool where the filter buttons exist. My AI Guide has a separate allowlist of permitted actions and can call the same implementations directly when the experimental API isn't available. My `webmcp-site.js` · Imperative API documentation

From the Playground to the AI Guide

I then added tools to the portfolio and connected them to the existing AI Guide. On the English site, you can open the chat and type “Show AI projects”. In a test, the Guide opened the projects page, activated the “AI / ML” filter, and left three cards visible. “Open the contact section” took me to the contact section. In both cases, the result was right there on the page, outside the chat window. Portfolio with the AI Guide

Switching languages turned out to be more interesting. “Switch the site to Polish” opened the Polish site. The Polish equivalent, “Przełącz stronę na polski”, got a text reply while the interface stayed in English. The code revealed a tiny detail with a visible effect. After the text was normalised, the word przełącz still contained ł, but the rule that spots commands expected a plain l. In a separate test, calling the tool directly through WebMCP switched the site back to English. That left me with two separate questions. Does the function work? And does the Guide know when to use it? Command handling code

Recognising commands is part of the code I added to the site. The AI Guide first checks whether a message looks like a request to do something. If it does, the Guide asks the model for a plan. When it gets no valid plan back, it tries to match the request with a few simple rules. The code checks the chosen function and its arguments against an allowlist. When a request takes the visitor to a different page, it can also remember the remaining steps across the page load.

WebMCP makes the tools available to a compatible agent in the browser. The built-in Guide can also call the same JavaScript functions directly when the browser lacks the necessary API. A change on the page tells me that the command took effect. To verify native WebMCP, I call the tool separately or check the mode in the Playground. AI Guide code · Integration code

Filters also made it clear that the current page matters. The filtering tool is available on the page that actually has the filters. In the chat, I can simply ask for AI projects. My code handles the order so the filter has somewhere to run.

The playlist that switched off the lights

Another demo from the Summit stuck with me, and it was less harmless than a project filter. There was a smart-home control page with a playlist containing a song called “Lights off”. An agent was meant to work with the music list but took text it encountered as an instruction to switch off the living-room lights. Chrome Developers describe a similar simulated demonstration: malicious instructions embedded in playlist metadata caused an unprotected agent to call a tool that controlled the lights. Chrome Developers' WebMCP security demo · Agent security guidance

There's an important distinction. The title “Lights off” should not, by itself, be a command. The problem starts when data — a track description, comment, search result, or tool response — pretends to be an instruction to the agent. That's indirect prompt injection. The person asked the agent to do one thing; someone else planted text in the material it would read, trying to make it do something else. Once an agent has tools that can change physical devices, this is more than an odd chat response.

I remembered something from the demo sounding like “restricted”. I couldn't find a restricted switch in the current WebMCP API that would magically block this. What the documentation does provide is untrustedContentHint, alongside a defensive technique called spotlighting. The first is a tool annotation saying its output may contain third-party or otherwise untrusted text. The second is something the agent implements: separating that text from instructions, for example by explicitly marking it as data that should be read but not obeyed.

For a hypothetical tool that reads a playlist, the declaration could look like this (this is an illustrative security example, not code deployed in my portfolio):

await document.modelContext.registerTool({
  name: 'get_playlist',
  description: 'Read tracks from a playlist.',
  inputSchema: { type: 'object', properties: {}, additionalProperties: false },
  annotations: {
    readOnlyHint: true,
    untrustedContentHint: true
  },
  execute: async () => JSON.stringify(await loadPlaylist())
});

readOnlyHint says that fetching the playlist doesn't change anything. untrustedContentHint warns that returned song titles and descriptions aren't authorized to issue new commands. These are signals, not automatic safeguards: the client must handle them, and the app still needs real permission checks and input validation. For high-consequence actions such as unlocking a door, consequentialHint: true signals that the browser or agent should obtain user confirmation. Trusted-origin restrictions, access control, and independent checks on whether a requested action actually came from the user matter just as much. WebMCP tool security · Security guidance for agent developers

The stakes on my portfolio are rather smaller: an agent can change the language or a project filter. That's part of why it was a good place to start. If I were exposing tools for submitting forms, buying things, or controlling devices, permission boundaries and user confirmation would have to be part of the design from day one.

Where else might this be handy?

If the language switch is within reach, clicking it is quicker. Things get more interesting when a request involves several steps. I can ask for AI projects and land straight in the relevant part of the catalogue. In a larger app, I can imagine opening a report with a particular date range or jumping to the right form with a few fields filled in for review. Before that form goes anywhere, I’d want to see a summary and decide whether to submit it myself.

WebMCP is still evolving, and native calls depend on browser support. On my site, I’d start by improving how the Guide handles a few Polish commands and seeing when a conversation really does save some digging through menus. After that, I’d like to try it on something slightly more complicated than a portfolio. The counter, at least, has made it to three. WebMCP status and testing in Chrome

Strona podpowiada, co potrafi

Jeśli agent obsługuje stronę przez zwykły interfejs, może szukać przycisku tak jak człowiek. Czyta etykiety, rozgląda się po menu i próbuje ustalić, co kliknąć. Na stronie z projektami musiałby najpierw znaleźć właściwą podstronę, potem odszukać filtry i skojarzyć „projekty AI” z etykietą „AI / ML”. Na mojej stronie dałoby się to zrobić. Na innej ten sam filtr mógłby być schowany w rozwijanym menu.

WebMCP to rozwijana propozycja standardu, dzięki któremu strona może sama udostępnić konkretne funkcje w otwartej karcie. Każde narzędzie ma nazwę, opis i określone dane wejściowe. Strona może więc wystawić funkcję „ustaw filtr projektów” i wymienić kategorie, które ta funkcja przyjmuje. Zgodny agent może wywołać ją z kategorią ai. To strona decyduje, jak ustawić filtr. U mnie korzysta z tego samego przycisku, który można nacisnąć ręcznie. Dokumentacja WebMCP w Chrome · Kod narzędzi portfolio

W praktyce ważne jest dla mnie to, że narzędzie daje się sprawdzić w oderwaniu od rozmowy. Mogę podać mu konkretną wartość i zobaczyć, jak zareaguje strona. Dopiero potem dokładam pytanie, czy agent wybrałby tę samą funkcję po przeczytaniu zwykłego zdania.

MCP w nazwie trochę miesza

W tym miejscu warto wyjaśnić jedną rzecz, bo sama nazwa może prowadzić na manowce. MCP i WebMCP nie są tym samym, choć oba pozwalają agentom korzystać z narzędzi. Kiedy słyszę „MCP”, myślę o Model Context Protocol: kliencie, serwerze, połączeniu z usługą i narzędziach dostarczanych zwykle przez backend. Agent może na przykład odpytać bazę albo uruchomić proces za pośrednictwem serwera MCP, nie otwierając w ogóle strony internetowej. W grę wchodzą komunikaty JSON-RPC oraz transporty takie jak stdio i HTTP.

WebMCP to z kolei Web Model Context Protocol — propozycja API przeglądarkowego inspirowana MCP, a nie „MCP uruchomione w JavaScripcie”. Kod narzędzia działa w kontekście otwartej strony i jej aktualnej sesji. Przeglądarka udostępnia opis funkcji agentowi, który potrafi z WebMCP korzystać. Gdy zamknę kartę, narzędzia tej strony przestają być dostępne. Na razie WebMCP udostępnia narzędzia, bez odpowiedników zasobów i promptów znanych z MCP. Sama funkcja strony może oczywiście komunikować się z backendem, ale WebMCP nie tworzy z tego backendowego serwera MCP.

Dla mojego eksperymentu różnica jest prosta: gdy proszę o pokazanie projektów AI, nie łączę się z osobnym serwerem MCP, który zarządza portfolio. Korzystam z funkcji samej strony, a jej efekt widzę od razu w interfejsie. Nazwy są podobne, ale to dwa różne miejsca, w których agent dostaje możliwość działania. Jak to wygląda pod spodem?

WebMCP nie wymaga pisania drugiego interfejsu dla agenta. W wariancie Imperative API strona rejestruje narzędzie przez document.modelContext.registerTool(). Poniżej uproszczony fragment oparty na moim webmcp-site.js. To ta sama idea co w działającym portfolio: agent podaje kategorię, a skrypt naciska istniejący przycisk filtra.

if ('modelContext' in document) {
  document.modelContext.registerTool({
    name: 'portfolio_filter_projects',
    description: 'Apply the project category filter.',
    inputSchema: {
      type: 'object',
      properties: {
        category: { type: 'string', enum: ['all', 'ai', 'automation', 'integration', 'product', 'commerce', 'data'] }
      },
      required: ['category'],
      additionalProperties: false
    },
    annotations: { readOnlyHint: false },
    execute: async ({ category }) => {
      const button = [...document.querySelectorAll('.filter-chip[data-filter]')]
        .find(el => el.dataset.filter === category);
      if (!button) throw new Error('Filter not found');
      button.click();
      return JSON.stringify({ success: true, category });
    }
  });
}

Najważniejsze nie jest tutaj click(), tylko kontrakt: nazwa, opis, inputSchema i execute. enum ogranicza wartości, które agent powinien podać, a sam kod dodatkowo sprawdza, czy dany filtr istnieje. W pełnej wersji narzędzie zwraca także liczbę widocznych projektów i ich nazwy. Rejestruję je tylko na podstronie, na której są przyciski filtrów. Mój AI Guide ma ponadto własny, jawny zestaw dozwolonych wywołań i może korzystać z tych samych implementacji także wtedy, gdy eksperymentalne API nie jest dostępne. Od Playgroundu do AI Guide

Potem dodałem narzędzia do portfolio i połączyłem je z istniejącym AI Guide. W angielskiej wersji strony można otworzyć czat i wpisać „Show AI projects”. W teście Guide przeszedł na podstronę projektów, zaznaczył filtr „AI / ML” i na liście zostały trzy karty. „Open the contact section” otworzyło sekcję kontaktu. W obu przypadkach efekt było widać na stronie, poza oknem rozmowy. Portfolio z AI Guide

Zmiana języka przyniosła ciekawszy wynik. „Switch the site to Polish” otworzyło polską wersję. Przy „Przełącz stronę na polski” czat odpowiadał tekstem, a interfejs zostawał po angielsku. W kodzie wyszła drobnostka z konkretnym skutkiem. Po uproszczeniu tekstu w słowie „przełącz” wciąż zostawało ł, a reguła rozpoznająca polecenia szukała zapisu z l. W osobnej próbie bezpośrednie wywołanie narzędzia przez WebMCP przełączyło stronę z powrotem na angielski. To pomogło rozdzielić dwa pytania. Czy funkcja działa? I czy Guide rozpoznaje, kiedy jej użyć? Kod rozpoznawania poleceń

Rozpoznawanie poleceń to część, którą dopisałem po stronie portfolio. AI Guide najpierw sprawdza, czy wiadomość wygląda na prośbę o działanie. Jeśli tak, prosi model o plan. Gdy nie dostanie poprawnego planu, próbuje dopasować polecenie za pomocą prostych reguł. Kod sprawdza też, czy wybrana funkcja i jej argumenty mieszczą się na liście dozwolonych. Przy przejściu między podstronami potrafi też zapamiętać kolejne kroki na czas przeładowania.

WebMCP odpowiada tu za udostępnianie narzędzi zgodnemu agentowi w przeglądarce. Wbudowany Guide ma też ścieżkę, która wywołuje te same funkcje bezpośrednio w JavaScripcie, gdy przeglądarka nie udostępnia potrzebnego API. Dlatego sama zmiana widoku mówi mi, że zadziałało polecenie. Żeby sprawdzić natywne WebMCP, wywołuję narzędzie osobno albo patrzę na tryb pracy w Playgroundzie. Kod AI Guide · Kod integracji

Przy filtrach szybko wyszło też, że znaczenie ma miejsce wywołania. Narzędzie do filtrowania jest dostępne na podstronie, na której rzeczywiście są filtry. W rozmowie proszę po prostu o projekty AI. To mój kod pilnuje kolejności, żeby filtr miał gdzie zadziałać.

Playlista, która wyłącza światło

Na Summit zapamiętałem jeszcze jeden pokaz, dużo mniej niewinny niż filtrowanie kart. Była strona do sterowania inteligentnym domem, a na niej playlista z utworem „Lights off”. Agent miał pracować z listą piosenek, ale z treści, którą odczytał, wyciągnął polecenie wyłączenia światła w salonie. W materiałach Chrome Developers jest opisany podobny demonstrator: złośliwa instrukcja została ukryta w metadanych playlisty, a agent w symulacji potraktował ją jak polecenie i użył narzędzia do sterowania oświetleniem. Pokaz bezpieczeństwa WebMCP – Chrome Developers · Dokumentacja o atakach na agentów

Warto tu rozróżnić dwie rzeczy. Sam tytuł „Lights off” nie powinien być rozkazem. Ryzyko pojawia się, kiedy tekst pochodzący z danych — opisu piosenki, komentarza, wyniku wyszukiwania albo odpowiedzi narzędzia — udaje instrukcję dla agenta. To właśnie indirect prompt injection. Użytkownik prosił o jedną rzecz, a ktoś umieścił wewnątrz odczytywanych danych próbę nakłonienia modelu do zrobienia czegoś innego. W połączeniu z narzędziami, które naprawdę zmieniają stan urządzeń, przestaje to być wyłącznie dziwna odpowiedź na czacie.

Pamiętałem z pokazu słowo brzmiące jak „restricted”. W aktualnym API nie znalazłem jednak przełącznika restricted, który sam blokowałby taki atak. Są za to untrustedContentHint i technika nazywana spotlighting. Pierwsza rzecz jest adnotacją przy narzędziu: informuje agenta, że wynik może zawierać obcą, niezaufaną treść. Druga dotyczy sposobu, w jaki sam agent odseparowuje takie dane od instrukcji, np. wyraźnie je oznacza i stosuje zasadę „czytaj jako dane, nie wykonuj jako polecenia”.

Przy hipotetycznym narzędziu odczytującym playlistę wyglądałoby to tak (to przykład bezpieczeństwa, a nie funkcja mojego portfolio):

await document.modelContext.registerTool({
  name: 'get_playlist',
  description: 'Read tracks from a playlist.',
  inputSchema: { type: 'object', properties: {}, additionalProperties: false },
  annotations: {
    readOnlyHint: true,
    untrustedContentHint: true
  },
  execute: async () => JSON.stringify(await loadPlaylist())
});

readOnlyHint mówi, że samo pobranie playlisty niczego nie zmienia. untrustedContentHint ostrzega, że zwrócone tytuły i opisy nie mają prawa wydawać nowych poleceń. To wskazówki, nie automatyczna blokada: klient musi je uwzględnić, a aplikacja musi pilnować uprawnień i walidować żądania. Dla działań o poważnych konsekwencjach, jak otwieranie zamka, istnieje consequentialHint: true, który sygnalizuje potrzebę potwierdzenia przez użytkownika. Do tego dochodzą ograniczenia do zaufanych domen, kontrola dostępu i osobne reguły, które nie pozwolą wykonać operacji tylko dlatego, że tak napisano w cudzym tekście. Bezpieczeństwo narzędzi WebMCP · Zalecenia dla twórców agentów

W moim portfolio stawka jest niewielka: agent może przełączyć język albo filtr. I właśnie na takim przykładzie wygodnie mi było zacząć. Gdybym miał wystawiać narzędzia do wysyłania formularzy, zakupów czy sterowania urządzeniami, granice uprawnień i potwierdzanie działań byłyby częścią rozwiązania od początku, a nie dodatkiem na końcu.

Gdzie przydałoby się to jeszcze?

Do zmiany języka na portfolio szybciej użyję przełącznika, jeśli mam go pod ręką. Ciekawiej robi się przy poleceniach, które składają się z kilku kroków. Mogę poprosić o projekty AI i od razu zobaczyć odpowiednią część katalogu. W większej aplikacji podobnie wyobrażam sobie otwarcie raportu z wybranym zakresem dat albo przejście do odpowiedniego formularza i uzupełnienie kilku pól do sprawdzenia. Przy wysłaniu formularza chciałbym już zobaczyć podsumowanie i sam zdecydować, czy go zatwierdzam.

WebMCP wciąż się zmienia, a natywne wywołania zależą od obsługi w przeglądarce. Na własnej stronie zacząłbym teraz od dopracowania kilku polskich poleceń i sprawdzenia, w których sytuacjach rozmowa rzeczywiście oszczędza szukania po menu.
