INTEGRATION / ARCHITECTURE

Integration is an ownership problem before it is an API problem

12 JUN 20269 MINJAN JĘDRZEJAK

A reliable API integration needs an agreed data contract, a source of truth, stable identifiers, exception handling and an owner. The API transports information; these decisions determine whether both systems understand and use it correctly.

Teams often describe integration as a technical connection.

An endpoint cannot resolve semantic conflict

Two systems can exchange a field named status.

Every handoff needs an owner

Who corrects an invalid record?

Architecture question

Do not ask only whether systems can connect.

Observability is part of the product

A durable integration exposes volume, latency and failures.

The API is the final expression

Once definitions and ownership are clear, implementation becomes easier.

A checklist before connecting two business systems

  • Source of truth: identify which system owns each business field.
  • Identity: choose a stable external ID and define how updates find an existing record.
  • Data contract: agree on types, required fields, units, time zones and status definitions.
  • Delivery: specify the trigger, frequency, pagination and expected delay.
  • Recovery: define retry limits, duplicate protection and a manual recovery route.
  • Operation: assign alert recipients, access ownership and a review schedule.

Webhook or scheduled synchronization?

A webhook is useful when the source can notify the receiving system about a change. Scheduled synchronization is useful when the source offers a queryable API but no suitable event. The choice should reflect the required delay and the ability to recover missed events. In either design, keep a checkpoint and periodically reconcile the source with the destination.

How can retries create duplicate records?

Imagine the destination saves an order but the response is lost. Retrying a create request can then save a second order. Treat a timeout as an unknown outcome. Use a stable business identifier, an idempotency key when supported, or a lookup before repeating the write. The destination needs a uniqueness rule because a check followed by an insert can still race with another request.

What should integration monitoring show?

Separate technical availability from data correctness. Record the event identifier, source and destination, processing time, attempt count and final status. Track expected versus processed records and the oldest unprocessed event. Avoid putting secrets or complete personal records into diagnostic logs. Give the process owner a clear way to find the affected item and its next action.
